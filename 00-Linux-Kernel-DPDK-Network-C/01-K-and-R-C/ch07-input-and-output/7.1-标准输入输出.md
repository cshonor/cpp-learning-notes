# 7.1 标准输入输出

## 本节讲什么

最底层的字符 I/O：**`getchar()`** / **`putchar()`**，以及 **`EOF`** 结束标记。第 1 章已用 `getchar` 做文件复制；本章系统展开流模型。

## 要点

- **`getchar()`**：从 **stdin** 读一个 `unsigned char` 转为 `int` 返回；无更多数据时返回 **`EOF`**
- **`putchar(c)`**：向 **stdout** 写一个字符
- **字符流抽象**：终端、管道、文件在 C 标准 I/O 层都是**连续字节序列**，区别在是否重定向、`FILE*` 绑定
- **`EOF`**：通常为 `-1`，表示流结束或错误（需结合 `feof`/`ferror` 区分，见 7.5、7.6）
- `getchar`/`putchar` 往往经 **stdio 缓冲**；`fflush(stdout)` 在交互提示后常用

## 示例

```c
#include <stdio.h>

int c;
while ((c = getchar()) != EOF)
    putchar(c);
```

重定向：`prog < in.txt > out.txt` —— 程序不变，stdin/stdout 换绑文件。

## 底层映射

| 场景 | 对应 |
|------|------|
| 串口字符流 | 逐字节 read/write，概念同 getchar |
| UEFI ConOut | 类 putchar 输出到 GOP/串口 |
| HFT 日志 | 热路径少用 stdio，但调试仍靠字符流 |

## getchar/putchar 与标准流的绑定关系

### 核心事实：硬编码绑定 stdin/stdout

`getchar()` 和 `putchar()` 在 `<stdio.h>` 里是宏，**固定**绑定到 stdin/stdout：

```c
#define getchar()  getc(stdin)        // 永远从 stdin 读
#define putchar(c) putc((c), stdout)  // 永远往 stdout 写
```

你**无法**让 `getchar` 从别的流读。要操作其他流，必须用通用版本：

| 函数 | 绑定的流 | 用途 |
|------|---------|------|
| `getchar()` | 固定 stdin | 快捷读 stdin |
| `putchar(c)` | 固定 stdout | 快捷写 stdout |
| `getc(fp)` / `fgetc(fp)` | 任意 `FILE*` | 从指定流读 |
| `putc(c, fp)` / `fputc(c, fp)` | 任意 `FILE*` | 往指定流写 |

> 7.1 的 getchar/putchar 是"便捷特化版"，7.5 的 fgetc/fputc 是"通用版"——加了个 `FILE*` 参数而已。

### getc/putc 是宏，fgetc/fputc 是函数

```c
int c = getc(fp);    // 宏：可能多次求值 fp（副作用陷阱）
int c = fgetc(fp);   // 函数：fp 只求值一次
```

- `getc`/`putc` 通常展开为内联宏，性能更好（省一次函数调用）
- 但如果 `fp` 参数有副作用（如 `getc(fp++)`），宏版本可能多次求值 → bug
- `fgetc`/`fputc` 是真正的函数，行为可预测，但多一次调用开销
- 实践中 `fp` 一般是简单变量，用 `getc`/`putc` 没问题；有疑虑就用 `fgetc`

### 底层展开：getchar 本质就是操作 stdin 的读缓冲区

`getchar()` → `getc(stdin)` 展开后：

```c
/* glibc 简化 */
(--stdin->_IO_read_end >= stdin->_IO_read_ptr)
    ? *(stdin->_IO_read_ptr++)    /* 缓冲区还有数据，直接取 */
    : __uflow(stdin)              /* 缓冲区空，触发 read() 填充 */
```

与 [7.1 流模型](#) 的三层抽象完全一致：getchar 操作的就是 stdin 这个 `FILE` 对象的读缓冲区指针。

### HFT/嵌入式视角

- getchar/putchar 是**便捷语法糖**，底层和 fgetc/fputc 一模一样
- HFT 热路径不会用任何 stdio 字符 I/O（锁 + 缓冲开销），直接 `write(fd, ...)` 或 mmap
- 嵌入式里 `printf` 到 UART 常被重定向为 `putchar` → `write(1, ...)` → UART 驱动

## fflush 底层澄清：系统调用是否因流不同而不同？

**结论：不不同。** `fflush` 无论作用于哪个 `FILE*`，底层走的都是同一个系统调用 `write(fd, buf, len)`，只是 `fd` 不同（stdout→1, stderr→2）。

### 三标准流的缓冲模式差异

| 流 | fd | 默认缓冲模式 | 缓冲区有数据？ | fflush 实际效果 |
|----|----|----|----|----|
| stdout → 终端 | 1 | 行缓冲（`\n` 触发刷） | 有（未到 `\n` 的部分） | **有实际意义**：强制刷出 |
| stdout → 文件 | 1 | 全缓冲（满块才刷） | 有（大量未写数据） | **有实际意义**：强制刷出 |
| stderr | 2 | 无缓冲 | 无（每字符直接 write） | **几乎空操作**：缓冲区本来就空 |

### 为什么底层统一？

`fflush(FILE *fp)` 的实现逻辑：

```c
/* glibc 简化逻辑 */
int fflush(FILE *fp) {
    if (fp->_IO_write_ptr > fp->_IO_write_base) {
        /* 有未写数据 → 调 write 刷出 */
        ssize_t n = write(fp->_fileno,
                         fp->_IO_write_base,
                         fp->_IO_write_ptr - fp->_IO_write_base);
        if (n < 0) return EOF;
        fp->_IO_write_ptr = fp->_IO_write_base;  /* 重置指针 */
    }
    return 0;
}
```

关键点：
- **`write()` 是同一个函数**，不管 fd 是 1 还是 2
- 区别仅在于：**有没有数据可刷**——这取决于缓冲模式
- stderr 无缓冲 = `setvbuf(stderr, NULL, _IONBF, 0)` → 每次 `fprintf(stderr, ...)` 直接调 `write(2, ...)` → 缓冲区始终空 → `fflush(stderr)` 没东西可刷
- stdout 行缓冲 = 未到 `\n` 的数据留在缓冲区 → `fflush(stdout)` 把它们 `write(1, ...)` 刷出

### 一句话总结

> **不是系统调用不同，是缓冲模式不同导致"有没有东西可刷"。** `write(fd, buf, len)` 对所有流都一样，fd 也只是参数。

### 进度条例子

```c
printf("Processing... ");   /* 无 \n，行缓冲不刷 */
fflush(stdout);             /* 强制 write(1, "Processing... ", 14) */
/* 做耗时操作时用户已看到提示 */
do_heavy_work();
printf("done\n");           /* \n 触发自动刷 */
```

如果是 `fprintf(stderr, "Processing... ");` 则**不需要** `fflush`——无缓冲模式直接就 `write(2, ...)` 了。

### fflush vs fsync 层次

```
用户缓冲区          内核页缓存          磁盘
  │                    │                 │
  │ fflush ──write()→  │                 │
  │                    │  fsync ────────→│
```

- **`fflush`**：用户态 stdio 缓冲区 → 内核（通过 `write` 系统调用）
- **`fsync(fd)`**：内核页缓存 → 磁盘（另一层系统调用）
- 两者**不在同一层**，`fflush` 之后数据到了内核，但未必到磁盘
